  - `NewLife.OllamaHub-net8.0.exe` 3,128,934 B
- CI 全绿：build job（Setup 双 SDK 44s → Build 4s → self-test×2 → publish×2 → Collect → Upload）+ release job 全部 success。
- **踩坑教训（重要，勿重犯）**：轮询 GitHub Actions 状态时用 `WebFetch` 反复请求**同一个** `/actions/runs/<id>/jobs` URL，命中 WebFetch 的 **15 分钟缓存**，一直返回 `in_progress` 的首个快照，导致误判「runner 卡死 12 分钟」，进而删 tag 重推（产生了一次重复 run）。实际当时 build 可能已完成。
  - 正确做法：轮询时给 URL 加随机参数（如 `?t=<timestamp>`）或改换 endpoint（`/jobs` ↔ `/runs?per_page=1` ↔ `/releases/tags/<tag>`）以绕开缓存；且先看 `runs` 列表的 status/conclusion 再下结论。
  - 另注意：删远端 tag 会**中断**该 tag 正在进行的 run；重推会起新 run，若旧 run 已建 Release，`action-gh-release` 会更新而非报错，但会浪费一次构建。

- 渲染方式：**Chrome headless（`--headless=new --screenshot --window-size=1080,1440 --force-device-scale-factor=1`）**，零第三方依赖；不装 puppeteer/playwright，也不依赖 Pillow（沙箱 `pip install pillow` 会被 SIGTERM 掐掉）。
- 可复用脚本：`marketing/render-cards.py`（按 `<!-- N 标题 -->` 切卡 → 生成单卡 HTML → 逐张截图 → 校验 PNG 尺寸），改文案后重跑即可覆盖图片。
- **排版治理经验（重要）**：
  1. **内容高度测量必须排除 `position:absolute` 子元素**——`.foot`（绝对定位页脚）会把「内容底部」虚报到 1376，掩盖真实留白（小红书 03 实测正文只到 867 却被判「良好」）。正确口径：只量非 absolute 的直接子元素 `getBoundingClientRect().bottom`。
  2. 安全线：卡片 1440 高、padding 92，正文底部应 ≤ ~1348；留白 >300px 即明显空。
  3. 按卡片类型加类放大间距：`.roomy`（列表）/`.roomy2`（两条列表→做成对比卡片块）/`.roomy3`（三条+页脚）/`.steps`（步骤 padding 100）/`.flowbig`（流程图节点）/`.gridbig`（12 格网格）。
  4. 中文孤字：`.card, .card *{text-wrap:pretty;}`（Chrome 117+），个别仍需在 HTML 里手动 `<br>` 控制断点。
  5. 标签贴页脚：`.card:has(.foot) .tags{margin-bottom:88px;}`。
- 注意：`body` 原有 `.card{margin-bottom:36px}`，单卡渲染时必须 `margin:0` + 去掉 `border-bottom`，否则出 1441px。
